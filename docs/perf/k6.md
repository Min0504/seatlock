# k6 부하 — 기획서 §8 3종 + 풀 고갈

로컬 Apple Silicon, Docker PostgreSQL 16 + Redis 7, 앱 단일 인스턴스. 2026-08-14.

```bash
# 전제: backend-nest/docker-compose.dev.yml
./bench/run-v4.sh
```

원본: `bench/out/v4-*-summary.json`. 사용자 JWT는 `v4-ctx.json` / `v4.env`에 있어 커밋하지 않는다.

## ① 1,000 VU × 좌석 10 — 초과판매 0

VU i 는 좌석 `i % 10` 을 친다. 좌석당 100명이 동시에 돌진.

| 지표 | 값 |
|---|---|
| 성공 (201) | **10** |
| 충돌 (409) | 990 |
| 그 외 5xx·타임아웃 | **0** |
| DB `show_seats` HELD (핫 10석) | **10** |
| p95 | 691 ms |
| max | 853 ms |

성공이 11이면 초과판매다. 조건부 UPDATE가 좌석당 승자 1명을 SQL 한 문장으로 고른다.
p95가 락 벤치마크의 단일 좌석 100명(116–149ms)보다 큰 이유: 이번엔 **10개 핫 행을 1,000 커넥션이 동시에** 두드린다. 정합성은 지연과 무관하게 10/10이다.

## ② 좌석맵 200 RPS × 15s — 캐시 on / Redis 다운

같은 회차 `GET /shows/{id}/seats`. 캐시 키 `show:{id}:seatmap` TTL 5s.

| | 요청 | 200 비율 | p50 | p95 | p99 | max |
|---|---:|---:|---:|---:|---:|---:|
| Redis 정상 (HIT) | 3,000 | 100% | 2.4 ms | **7.2 ms** | 18 ms | 72 ms |
| Redis stop (DB 폴백) | 3,001 | 100% | 4.8 ms | **31 ms** | 118 ms | 205 ms |

캐시 히트는 DB 커넥션을 안 잡는다(`ShowService.getSeatMap`에 `@Transactional` 없음). Redis가 죽어도 **기능은 유지**되고 p95만 약 4배로 는다. 매 요청이 `connect-timeout 300ms`를 다 쓰는 것은 아니다 — Lettuce가 끊긴 뒤 빠르게 실패하고 CacheClient가 예외를 삼킨다.

Redis 다운 중 선점 API는 **201**. 정합성 경로는 캐시를 쓰지 않는다. 재현: `LEAVE_DOWN=1 docs/chaos/redis-kill.sh`.

## ③ 같은 Idempotency-Key 동시 50

한 예매에 키 하나. 더블클릭·클라이언트 타임아웃 재시도를 흉내 낸다.

| 지표 | 값 |
|---|---|
| 201 (결제 실행) | **1** |
| 200 (재생) | 1 |
| 409 `PAYMENT_IN_PROGRESS` | 48 |
| `payments` 행 | **1** |
| p95 | 76 ms |

실행은 UNIQUE 선점 INSERT 1회뿐이다. 409는 재실행이 아니라 "잠깐 뒤에 같은 키로 다시" 신호다.

## 보너스 — 커넥션 풀 고갈 → 503

운영 기본은 `HIKARI_MAX_POOL=10`, `HIKARI_CONNECTION_TIMEOUT_MS=3000` (무한 대기 금지).

재현은 풀을 일부러 작게: **pool=2, timeout=500ms, 300 VU**.

| 지표 | 값 |
|---|---|
| 201/409 (처리됨) | 238 |
| **503 SERVICE_UNAVAILABLE** | **62** |
| p95 | 905 ms |

`pool=1` 은 Flyway 부팅이 두 번째 커넥션을 못 받아 기동 자체가 실패한다. 풀 하한은 "마이그레이션+헬스체크가 동시에 살아 있는 2"가 실측 하한이다.
