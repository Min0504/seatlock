# SeatLock — 좌석 선점형 공연 예매 시스템

> **포트폴리오 포지션: 플래그십 (1순위, 가장 먼저 시작).**
> 로드맵의 v1(NestJS 뼈대) → v2(동시성) → v3(Spring 포팅) → v4(운영)가 이 프로젝트 하나로 이어진다.
> "같은 도메인을 NestJS와 Spring으로 두 번 구현"하는 것 자체가 차별화 포인트다.

---

## 1. 프로젝트 기본 정보

| 항목 | 내용 |
|------|------|
| 프로젝트명 | SeatLock (시트락) |
| 한 줄 설명 | 인기 공연 오픈 순간 수천 명이 같은 좌석에 몰려도 **초과판매 0건**을 보장하는 좌석 예매 API |
| 목적 | 동시성 문제를 "일부러 재현 → 여러 방법으로 해결 → 부하테스트로 수치 검증"하는 전 과정을 증명 |
| 예상 사용자 | 관객(예매), 공연 기획사(공연·좌석 관리) — 가상의 소규모 티케팅 서비스 |
| 핵심 문제 | 동시 요청 상황에서 하나의 좌석이 두 명에게 팔리는 문제(race condition), 선점 후 미결제 좌석의 회수, 결제 중복 처리 |
| 해결 방법 | DB 원자적 조건부 UPDATE를 기본으로 비관적 락·낙관적 락·Redis 분산락을 **비교 구현**, 선점 TTL + 스케줄러 이중화, 멱등성 키 |
| 예상 개발 기간 | v1~v2: 6주 (주 15시간) / v3 포팅: 4~6주 / v4 운영: 2~3주 |
| 난이도 | 중 (v1) → 중상 (v3~v4) — 단계별로 올라가는 구조라 시작 부담이 낮다 |
| 핵심 역량 | **동시성 제어, 트랜잭션, 캐싱, 인증(JWT Rotation), 부하테스트, NestJS→Spring 포팅** |
| 클라이언트 | **웹(반응형 SPA)** — 좌석맵 시연 화면. `frontend/` 폴더 분리, 판단 근거는 §3 |

### 언어 선택 근거 (내 전략과의 연결)

- v1~v2는 **NestJS(TypeScript strict)** — 익숙한 스택으로 "작더라도 돌아가는 완성"을 먼저 만든다. 완성 경험이 우선.
- v3에서 **Java 17 + Spring Boot 3로 포팅** — 설계가 이미 검증됐으므로 순수하게 Spring/JPA 학습에 집중할 수 있다. 완료하면 이력서에 Java/Spring 기재 가능 → 국내 기업 풀 70~80% 진입. **이 포팅이 취업 계획 전체의 관문이다.**
- 두 구현을 레포에 함께 남긴다(`/nest`, `/spring`). 면접에서 "프레임워크가 바뀌어도 유지되는 것(도메인 규칙·SQL·트랜잭션 경계)과 바뀌는 것(DI·ORM·미들웨어)"을 직접 비교 설명할 수 있다.

## 2. 핵심 기능 (기능마다 백엔드 문제 명시)

| 기능 | 내용 | 여기서 발생하는 백엔드 문제 |
|------|------|------------------------------|
| 회원가입/로그인 | 이메일+비밀번호, bcrypt 해싱 | 비밀번호 저장 정책, 타이밍 공격 |
| 토큰 관리 | Access 15분 / Refresh 14일, **Rotation + 재사용 탐지** | 탈취된 Refresh Token이 재사용될 때 세션 계열(family) 전체 폐기 |
| 공연/회차/좌석 등록 | ADMIN 전용. 공연장 좌석 템플릿 → 회차별 좌석 인스턴스 생성 | 회차 생성 시 수천 행 bulk insert 성능 |
| 공연 검색 | 제목/출연진 부분 일치 + 날짜 필터 | LIKE '%검색어%'는 인덱스를 못 탐 → pg_trgm GIN 인덱스 |
| 좌석맵 조회 | 회차별 좌석 상태(판매가능/선점/판매완료) | 오픈 직후 초당 수천 조회 → Redis 캐시 + 무효화 정합성 |
| **좌석 선점(hold)** | 선택한 좌석을 5분간 잠금 | **동일 좌석 동시 선점 — 이 프로젝트의 심장** |
| 선점 만료 | 5분 내 미결제 시 자동 해제 | TTL 이벤트 유실 가능성, 스케줄러 중복 실행 |
| 예매 확정(결제) | mock PG 연동, 결제 성공 시 RESERVED 확정 | 중복 클릭/네트워크 재시도로 인한 **이중 결제**, PG 타임아웃 시 상태 불일치 |
| 예매 취소 | 상태 전이(RESERVED→CANCELED), 좌석 원복 | 취소와 신규 선점의 경합, 환불 mock |
| 포스터 업로드 | S3 Presigned URL 방식 | 서버 경유 없는 업로드, 파일 타입/크기 검증 |
| 관리자 판매 통계 | 회차별 판매율/매출 집계 | 집계 쿼리 성능, 실시간 vs 배치 집계 |
| (v4 선택) 대기열 | 오픈 순간 유입 제어 | Redis Sorted Set 기반 순번, 입장 토큰 |

## 3. 기술 스택

| 구분 | v1~v2 (NestJS) | v3~v4 (Spring, 최종형) | 선정 이유 |
|------|----------------|------------------------|-----------|
| 언어 | TypeScript 5 (strict) | Java 17 | 전략: TS로 완성 → Java로 관문 통과 |
| 프레임워크 | NestJS 11 | Spring Boot 3.x | 국내 채용 표준. DI·모듈 구조가 유사해 포팅 학습 효율이 높음 |
| ORM | Prisma | Spring Data JPA (+ 필요시 QueryDSL) | JPA 영속성 컨텍스트·락 어노테이션이 면접 단골 |
| DB | PostgreSQL 16 | PostgreSQL 16 (동일) | 스택 무관 공통 자산. 조건부 UPDATE·pg_trgm 활용 |
| 캐시 | Redis 7 | Redis 7 (동일) | 좌석맵 캐시, 선점 TTL, (v4) 대기열 |
| 인프라 | Docker Compose | + AWS EC2, RDS, S3 | 로컬 환경 재현성 → 실배포 |
| CI/CD | GitHub Actions | 동일 | 테스트 통과 시에만 배포 |
| 부하테스트 | k6 | k6 (동일) | "초과판매 0건" 수치 증명 도구 |
| 모니터링(v4) | — | Prometheus + Grafana | 운영 서사(v4)의 핵심 |

넣지 않는 것: Kafka·Elasticsearch·MSA — 이 규모에서 문제 해결에 불필요. "왜 안 썼는가"도 면접 답변이 된다 (검색은 pg_trgm으로 충분, 이벤트 스트림이 필요한 도메인이 아님).

### 클라이언트 결정 — 웹 vs 앱

| 후보 | 판단 |
|------|------|
| 모바일 앱 | 실서비스 티케팅 앱이 존재하는 형태라 유일한 앱 후보였으나 탈락 — 설치·스토어 장벽 때문에 심사자가 즉시 볼 수 없고, 좌석맵은 작은 화면에서 불리 |
| **웹 (채택)** | ① 링크 클릭 한 번으로 시연 ② 좌석맵은 넓은 화면이 정합 ③ **브라우저 창 2개로 같은 좌석을 동시에 잡는 동시성 데모** — 이 프로젝트의 킬러 데모는 웹에서만 가능 ④ 실제 예매 오픈 트래픽도 PC 웹 중심 |

- 스택: Vite + React + TypeScript(strict) + Tailwind. 화면은 5개만 — 공연 목록/검색 → 공연 상세(회차 선택) → **좌석맵(상태 색상 + 선점 5분 카운트다운)** → 결제(재클릭해도 안전한 Idempotency-Key 데모) → 내 예매
- 원칙: **프론트는 백엔드를 보여주는 유리창.** AI 도구로 빠르게 생성하고 전체 개발 시간의 15%를 넘기지 않는다. 관리자 기능은 화면 없이 Swagger로 충분

### 저장소 구조 (프론트/백엔드 폴더 분리)

```text
seatlock/

├── frontend/       # 웹 좌석맵 SPA — 시연용
```

### Git·주석 전략 (커밋·푸시·PR·코드 주석) — 백엔드와 프론트를 다르게

> 원칙: **백엔드는 공부의 기록, 프론트는 결과물만.** 심사자·면접관이 읽는 것은 백엔드의 커밋·PR 이력이다.

| 구분 | 백엔드 (학습의 본체) | 프론트엔드 (거들 뿐) |
|------|---------------------|---------------------|
| 커밋 | **1커밋 = 1개념**, 메시지에 무엇/왜 — `feat(hold): 선점을 조건부 UPDATE로 원자화 — check-then-act race 제거` | 화면 단위 뭉텅이 허용 — `fe: 좌석맵 화면` (AI 생성 코드 그대로 커밋 OK) |
| 브랜치 | GitHub Flow. **핵심 문제(§7) 1개 = 브랜치 1개** — `feat/hold-concurrency`, `feat/idempotent-payment`, `port/spring-auth` | `fe/*` 브랜치 하나로 화면 몇 개씩 묶어 진행 |
| PR | **혼자여도 PR을 연다** — 본문에 문제→해결→증거(동시성 테스트 결과·k6 수치) 기록, CI 초록 없이 머지 금지, 셀프 리뷰 코멘트로 학습 포인트 남김 | 생략 가능(main 직행) 또는 화면 묶음당 1개 — 스크린샷 한 장이면 충분, squash 머지 |
| PR 단위 | 핵심 문제 1개 = PR 1개 (Phase당 2~4개) — 면접에서 PR 링크가 곧 증거 자료 | 프로젝트 전체에서 PR 1~2개 |
| 푸시 | 매일 푸시 (미완성이면 WIP 브랜치로), main force push 금지 | 동일 |
| 이력 관리 | 락 4종 비교 브랜치(`experiment/pessimistic-lock` 등)는 **머지하지 않고 보존** → README에서 링크. `backend-nest/`는 v3 착수 시 커밋 동결 선언 | 이력 가치 없음 — 정리 없이 진행 |

**주석 규칙 — 코드가 곧 교재가 되도록:**

- **백엔드: 핵심 로직마다 설명 주석 필수.** "무엇을 하는지"가 아니라 **왜 이 방식인지**(문제 상황 → 대안 → 선택 이유)를 적는다. 예 — 조건부 UPDATE 위에: `// SELECT 후 UPDATE로 나누면 두 트랜잭션이 그 틈에 같은 좌석을 통과한다(check-then-act race) → WHERE status='AVAILABLE' 조건부 UPDATE 한 문장으로 원자화. 비관적 락 대비 트레이드오프는 docs/lock-benchmark.md`. 몇 달 뒤 코드만 읽어도 학습 내용이 복원되고, 면접 직전 복습 자료가 된다.
- **프론트: 주석 최소.** AI가 생성한 코드 그대로 두고, 백엔드 계약과 닿는 지점(hold 만료 카운트다운, 409 CONFLICT 처리)에만 한 줄 남긴다.

## 4. 아키텍처

```
[웹 프론트엔드 (frontend/ 좌석맵 SPA) + Swagger]
        │ HTTPS
        ▼
[Nginx (reverse proxy, rate limit 1차)]
        │
        ▼
[API Server — NestJS(v1~v2) → Spring Boot(v3~)]
   │           │                    │
   │           │                    └──> [S3] 포스터 (Presigned URL 발급만 서버가 담당)
   │           ▼
   │      [Redis 7]
   │        · 좌석맵 캐시 (show:{id}:seatmap)
   │        · 선점 TTL 키 (hold:{showSeatId})
   │        · (v4) 대기열 Sorted Set
   ▼
[PostgreSQL 16 (RDS)]  ←— 좌석 상태의 "최종 권위(source of truth)"
        ▲
[Scheduler (@Scheduled / @nestjs/schedule)]
        · 만료 선점 회수 (DB expires_at 기준 — Redis TTL의 보정자)

[Prometheus] ←(scrape)— API Server /metrics     [Grafana] — 대시보드 (v4)
```

**데이터 흐름 (예매 성공 경로):**
좌석맵 조회(Redis 캐시) → 좌석 선점 POST(DB 조건부 UPDATE로 원자적 선점 + Redis TTL 세팅) → 결제 POST(멱등성 키 검증 → mock PG 승인 → 트랜잭션 안에서 HELD→RESERVED 전이) → 좌석맵 캐시 무효화.

**원칙: Redis는 성능·편의(캐시/TTL 알림), PostgreSQL이 항상 최종 권위.** Redis가 전부 날아가도 데이터 정합성은 깨지지 않아야 한다.

## 5. 데이터베이스 설계

### users — 사용자
| 컬럼 | 타입 | 제약 |
|------|------|------|
| id | BIGSERIAL | PK |
| email | VARCHAR(255) | UNIQUE, NOT NULL |
| password_hash | VARCHAR(255) | NOT NULL (bcrypt) |
| role | VARCHAR(20) | NOT NULL, 'USER' / 'ADMIN' |
| created_at / updated_at | TIMESTAMPTZ | NOT NULL |

### refresh_tokens — 토큰 회전 추적
| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | UUID PK | 토큰 식별자 (JWT jti 클레임과 매칭) |
| user_id | BIGINT FK→users | 인덱스 |
| family_id | UUID | **로그인 1회 = 1 family.** 재사용 탐지 시 family 전체 폐기 |
| token_hash | VARCHAR | 원문 저장 금지, SHA-256 해시만 |
| used | BOOLEAN | rotation으로 소진되면 true — true인 토큰이 다시 오면 탈취 신호 |
| expires_at | TIMESTAMPTZ | 인덱스 (만료 배치 삭제용) |

### performances — 공연
| 컬럼 | 타입 | 제약 |
|------|------|------|
| id | BIGSERIAL PK | |
| title | VARCHAR(200) | NOT NULL |
| description | TEXT | |
| poster_url | VARCHAR(500) | S3 키 |
| venue_id | BIGINT FK→venues | |
| search_text | TEXT | title+출연진 결합 — **GIN(pg_trgm) 인덱스** |

### venues / seats — 공연장과 좌석 템플릿
- venues: id PK, name, address
- seats: id PK, venue_id FK, section(구역), row_no, seat_no, **UNIQUE(venue_id, section, row_no, seat_no)** — 물리 좌석은 공연과 무관한 불변 템플릿 (정규화: 좌석 정보를 회차마다 복사하지 않기 위해 분리)

### shows — 회차
| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | BIGSERIAL PK | |
| performance_id | BIGINT FK | 인덱스 |
| starts_at | TIMESTAMPTZ | 공연 시각 |
| ticket_open_at | TIMESTAMPTZ | 예매 오픈 시각 (오픈 전 예매 차단) |

### show_seats — 회차별 좌석 인스턴스 ★ 이 프로젝트의 심장
| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | BIGSERIAL PK | |
| show_id | BIGINT FK→shows | |
| seat_id | BIGINT FK→seats | |
| price | INT | 회차·구역별 가격 |
| status | VARCHAR(20) | 'AVAILABLE' / 'HELD' / 'RESERVED' |
| hold_user_id | BIGINT NULL | 선점자 |
| hold_expires_at | TIMESTAMPTZ NULL | 스케줄러 회수 기준 — **부분 인덱스** `WHERE status='HELD'` |
| version | INT DEFAULT 0 | 낙관적 락 실험용 (JPA @Version) |
| | | **UNIQUE(show_id, seat_id)** — 같은 회차에 같은 좌석 중복 생성 차단 |

> 설계 판단: "예매 가능 여부"를 별도 테이블(inventory)로 빼지 않고 show_seats.status 한 컬럼으로 관리한다.
> 좌석제 공연은 좌석 하나가 재고 1이라 수량 차감 모델이 불필요하고, 상태 전이(AVAILABLE→HELD→RESERVED)가 도메인 그 자체이기 때문. (수량 기반 재고는 PointLedger·일반 커머스의 문제)

### reservations / reservation_seats — 예매와 예매-좌석 (1:N)
- reservations: id PK, user_id FK(인덱스), show_id FK, status('PENDING'/'CONFIRMED'/'CANCELED'), total_price, created_at

## 7. 핵심 백엔드 문제 (문제→원인→해결→선택 이유→비교→트레이드오프)

### 문제 1. 동일 좌석 동시 선점 — 초과판매 ★

- **문제:** 좌석 A가 AVAILABLE인 것을 두 요청이 동시에 읽고, 둘 다 HELD로 바꿔 두 명 모두 "선점 성공" 응답을 받는다.
- **원인:** check(조회)와 act(변경) 사이의 시간 간격. 애플리케이션 레벨 if문은 동시성 앞에서 무력하다.
- **해결(채택): DB 원자적 조건부 UPDATE**
  ```sql
  UPDATE show_seats
     SET status='HELD', hold_user_id=:uid, hold_expires_at=now()+interval '5 min'
   WHERE id = ANY(:seatIds) AND status='AVAILABLE';
  -- affected rows != seatIds.length 이면 전체 롤백 + 409
  ```
- **왜 이 방법인가:** 검사와 변경이 한 문장에서 원자적으로 일어나 race 자체가 성립하지 않는다. 락 대기가 없고(실패는 즉시 0 row), 코드가 단순하다.
- **다른 방법과 비교 (전부 브랜치로 구현해 벤치마크한다):**
  | 방법 | 원리 | 장점 | 단점 |
  |------|------|------|------|
  | 조건부 UPDATE (채택) | WHERE로 상태 검사+변경 원자화 | 대기 없음, 단순, DB 하나로 충분 | 복잡한 다단계 로직엔 부적합 |
  | 비관적 락 `SELECT ... FOR UPDATE` | 행 잠금 후 검사·변경 | 다단계 검증 로직 가능 | 락 대기·커넥션 점유, 데드락 가능(→ 좌석 ID 정렬로 예방) |
  | 낙관적 락 (JPA @Version) | 커밋 시 버전 충돌 감지 | 락 없음, 충돌 드문 도메인에 적합 | 티케팅은 충돌이 기본값 → 재시도 폭증 |
  | Redis 분산락 (Redisson) | DB 밖에서 선점권 직렬화 | DB 부하 차단, 다중 인스턴스 대응 | Redis 장애 시 락 소실 위험, 인프라 복잡도 증가 |
- **트레이드오프:** 조건부 UPDATE는 "선착순 실패는 즉시 실패"라는 UX를 강제한다(대기 없음). 좌석 경합이 극단적이면 DB 커넥션이 병목이 되는데, 그 시점의 정답은 락 튜닝이 아니라 **대기열로 유입 자체를 제어**하는 것(v4). 이 판단 과정 전체가 면접 답변이 된다.

### 문제 2. 선점 만료 처리 — 유령 좌석 방지

- **문제:** 선점 후 결제하지 않고 이탈하면 좌석이 영구 HELD로 남는다.
- **원인:** 선점은 상태를 바꾸지만, "5분 뒤"라는 미래 시점에 되돌릴 주체가 없다.
- **해결(채택): 이중화 — ① Redis TTL 키 + keyspace notification으로 즉시 해제(빠른 경로), ② DB `hold_expires_at` 기준 30초 주기 스케줄러(최종 권위)**
  ```sql
  UPDATE show_seats SET status='AVAILABLE', hold_user_id=NULL, hold_expires_at=NULL
   WHERE status='HELD' AND hold_expires_at < now();
  ```
- **왜:** Redis expired 이벤트는 **전달 보장이 없다**(pub/sub 유실, 재시작 시 소실). 알림은 UX(즉시성)용, 정합성은 DB 스케줄러가 책임지는 구조가 안전하다.
- **비교:** 지연 큐(BullMQ delayed job)도 가능하지만 이 프로젝트에 큐를 도입할 다른 이유가 없어 과함(큐는 HookRelay의 주제). 조회 시점 lazy 만료 판정(`status='HELD' AND expires_at<now()`이면 AVAILABLE로 간주)은 스케줄러 주기 사이의 공백까지 메꾼다 — 3중 방어.
- **트레이드오프:** 스케줄러 주기(30초)만큼 좌석 반환이 늦을 수 있다. 서버 2대면 스케줄러가 중복 실행되는데, 위 UPDATE는 멱등이라 안전 — 단 "멱등이라 안전하다"를 인지하고 설계했음을 문서화한다 (비멱등 작업이면 ShedLock 필요 — PointLedger에서 다룸).

### 문제 3. 결제 멱등성 — 이중 결제 방지

- **문제:** 사용자의 더블클릭, 클라이언트 재시도, 게이트웨이 타임아웃 재전송으로 결제 API가 두 번 실행된다.
- **원인:** HTTP는 재시도를 막을 수 없고, "한 번만 실행"은 서버가 보장해야 할 책임이다.
- **해결(채택):** 클라이언트가 `Idempotency-Key`(UUID)를 생성해 헤더로 전송 → 서버는 payments.idempotency_key **UNIQUE 제약**에 INSERT하는 것으로 선점 → 충돌(23505) 시 기존 레코드의 상태를 조회해 그대로 반환. PENDING이면 "처리 중" 응답(409)으로 동시 중복 실행 차단.
- **왜:** 유니크 제약은 DB가 보장하는 가장 값싸고 확실한 직렬화 장치다. 애플리케이션 메모리 기반 중복 체크는 서버가 2대가 되는 순간 무너진다.
- **비교:** Redis SETNX로 키 선점도 가능하나 결제처럼 돈이 걸린 기록은 TTL로 증발하면 안 되므로 DB가 맞다. 응답 캐싱까지 하려면 요청 바디 해시를 함께 저장해 same-key-different-body를 422로 거른다.
- **트레이드오프:** 키 생성 책임이 클라이언트에 있다 — API 문서에 계약으로 명시해야 하고, Swagger 예시와 E2E 테스트로 강제한다.

### 문제 4. Refresh Token Rotation과 탈취 탐지

- **문제:** Refresh Token이 14일 유효하므로 탈취되면 장기간 세션이 도용된다.
- **원인:** 긴 수명 토큰의 숙명. 짧게 만들면 UX가 나빠진다.
- **해결(채택):** refresh 요청마다 새 토큰 쌍 발급 + 이전 토큰 `used=true` 처리(Rotation). **used된 토큰이 다시 오면 = 탈취범과 정상 사용자 둘 다 토큰을 쓴 상황** → 해당 family_id 전체 폐기, 재로그인 강제.
- **왜:** 서버가 상태(used/family)를 가지면 "재사용"이라는 명확한 탈취 신호를 잡을 수 있다. 완전 stateless JWT는 이 탐지가 불가능하다.
- **비교:** ① 순수 stateless(재사용 탐지 불가) ② 세션 방식(매 요청 DB 조회 — Access까지 상태화하는 비용) ③ 채택안은 중간: Access는 stateless 15분, Refresh만 상태 추적 — 검증 비용은 refresh 시에만 발생.
- **트레이드오프:** refresh_tokens 테이블 관리(만료 행 정리 배치)와 동시 refresh 경합(두 탭이 동시에 갱신 → 한쪽 실패) 처리가 필요. Todayskin에서 JWT 기본만 했다면, 여기서 rotation까지 발전시키는 성장 서사가 된다.

### 문제 5. 좌석맵 캐시 정합성

- **문제:** 좌석맵을 Redis에 캐싱하면 조회는 빨라지지만, 선점/결제 순간 캐시가 낡은 상태(stale)가 된다.
- **원인:** 캐시와 DB라는 두 저장소에 같은 사실이 존재 — 분산 시스템 정합성 문제의 축소판.
- **해결(채택):** 상태 변경 트랜잭션 **커밋 후** 캐시 키 삭제(invalidate-on-write) + TTL 5초 안전망. 예매 확정 같은 "진실"은 항상 DB에서 재검증하므로, 좌석맵의 5초 지연은 UX 문제일 뿐 정합성 사고가 아니다 — **"어디까지 낡아도 되는가"를 도메인 기준으로 정의**한 것이 포인트.
- **비교:** write-through(변경 시 캐시 재작성)는 쓰기마다 좌석맵 전체 직렬화 비용 발생 + 동시 쓰기 순서 역전 위험. 삭제 방식이 단순하고 안전하다. TTL만 쓰는 방식은 오픈 순간의 폭주 조회에서 김빠진 데이터를 5초간 보여줌 — 삭제+TTL 조합이 균형점.
- **트레이드오프:** 삭제 직후 첫 조회가 DB를 때린다(cache stampede). 오픈 직후엔 이 미스가 몰릴 수 있어, 좌석맵 재구성 시 분산락 1개로 rebuild를 직렬화하는 옵션을 v4에서 실험한다.

| # | 장애 | 영향 | 대응 설계 |
|---|------|------|-----------|
| 1 | **Redis 다운** | 좌석맵 캐시·TTL 알림 소실 | 캐시 조회를 try-catch로 감싸 **DB 직행 폴백**(기능 유지, 성능만 저하). 만료 처리는 어차피 DB 스케줄러가 권위라 정합성 무손상. 복구 후 캐시 자연 재적재 — "Redis가 죽어도 서비스는 산다"를 카오스 테스트(컨테이너 kill)로 증명 |
| 2 | **mock PG 타임아웃** | 결제가 됐는지 안 됐는지 모르는 상태 | 결제는 PENDING으로 기록 → 타임아웃 시 PG 상태조회 API로 확인 → 승인이면 확정, 미승인이면 실패 처리 + 선점 유지시간 내 재시도 안내. **"모른다"를 상태로 모델링**하는 것이 핵심 |
| 3 | **DB 커넥션 고갈** | 전 API 대기·타임아웃 | HikariCP 타임아웃 짧게(3s) + 즉시 503 반환(무한 대기 금지), k6로 고갈 재현 → 풀 사이즈 근거 튜닝, 슬로우 쿼리 로그로 원인 추적 |
| 4 | 스케줄러 서버 중복 실행 | 만료 회수 2회 실행 | 해당 UPDATE는 멱등이라 무해함을 문서화. 비멱등 작업 추가 시 ShedLock 도입 기준 명시 |
| 5 | 취소와 신규 선점 경합 | 취소 직후 좌석 상태 혼선 | 취소도 조건부 UPDATE(WHERE status='RESERVED')로 원자화, 상태 기계 전이표를 코드와 문서로 고정 |

각 장애는 **재현 스크립트**(컨테이너 kill, 지연 주입)와 함께 `docs/incident/`에 1장짜리 리포트(현상→원인→조치→재발방지)로 남긴다 → v4의 "장애 리포트" 산출물.

## 11. 테스트 전략

| 레벨 | 도구 (Nest / Spring) | 반드시 검증할 것 |
|------|----------------------|------------------|
| Unit | Jest / JUnit5+Mockito | 상태 전이 규칙(HELD에서만 RESERVED 가능), 금액 계산, 만료 판정 로직 |
| Integration | Testcontainers(PostgreSQL, Redis) 양쪽 동일 | 조건부 UPDATE 동작, 부분 유니크 인덱스, rotation 재사용 탐지 |
| **동시성** | Promise.all 100개 / ExecutorService+CountDownLatch 100스레드 | **같은 좌석 선점 → 성공 정확히 1건** (이 테스트가 프로젝트의 존재 증명) |
| API(E2E) | Supertest / RestAssured | 인증 플로우 전체, 멱등성 키 계약(같은 키+다른 바디=422) |
| 부하 | k6 | §8의 3개 시나리오, 결과 수치 README 기재 |

CI: PR마다 unit+integration 실행(Testcontainers는 GitHub Actions에서 도커 지원), main 머지 시 배포. **테스트 없이 머지 불가 규칙을 스스로에게 강제** — 커밋 이력 자체가 포트폴리오다.

## 12. 배포

```
GitHub push → Actions: lint+test → Docker build → GHCR push
  → EC2 (docker compose pull & up -d)   # v3까지는 단순 SSH 배포
인프라: EC2 t3.small (API+Redis+Nginx) + RDS PostgreSQL(프리티어) + S3(포스터) + CloudWatch 기본
프론트: frontend/ 빌드 산출물을 S3+CloudFront 정적 호스팅 (AWS 학습 연계, 백엔드와 배포 수명주기 분리)
v4: Prometheus+Grafana 컨테이너 추가, (선택) EC2 2대+Nginx LB로 수평 확장 실험
```
현실 기준: ECS/EKS는 이 규모에 과함 — "왜 안 썼나"를 답변으로 준비. 무중단 배포는 v4에서 compose 기반 blue-green(포트 스왑)으로 맛본다.

## 14. 학습 가이드 — 코드를 하나씩 보며 공부하는 법

**규칙: 1커밋 = 1개념.** 커밋 메시지에 "무엇을/왜"를 남겨 커밋 로그 자체를 교재로 만든다. (예: `feat: 좌석 선점을 조건부 UPDATE로 원자화 — check-then-act race 제거`)

| Phase | 여기서 공부하는 개념 | 끝나고 스스로 답할 질문 |
|-------|---------------------|------------------------|
| 0 | NestJS 모듈/DI, DTO 검증, Prisma 스키마→마이그레이션, 레이어드 아키텍처 | "요청이 컨트롤러→서비스→DB까지 가는 경로를 코드 순서로 말할 수 있는가?" |
| 1 | 트랜잭션, race condition, 원자성, 인덱스와 유니크 제약 | "내 코드에서 race가 발생하는 정확한 두 줄은 어디였나?" |
| 2 | 멱등성, 외부 연동 타임아웃, CI/CD 파이프라인, 리버스 프록시 | "결제 버튼을 3번 눌러도 안전한 이유를 DB 제약으로 설명할 수 있는가?" |
| 3 | JPA 영속성 컨텍스트, 지연로딩, @Version, @Transactional 전파, Spring Security 필터 체인 | "Prisma와 JPA에서 같은 N+1이 왜 다르게 생기고 다르게 풀리는가?" |
| 4 | 캐시 무효화, TTL, 토큰 rotation, GIN 인덱스 | "캐시가 5초 낡아도 되는 근거를 도메인 언어로 말할 수 있는가?" |
| 5 | 메트릭(RED), 히스토그램/퍼센타일, 부하테스트 설계 | "p95가 튀면 어디부터 보는가?" |

**코드 읽기 순서(복습용):** ① prisma/schema(또는 entity) — 데이터가 곧 도메인 ② 좌석 선점 서비스 — 심장 ③ 동시성 테스트 코드 ④ 인증 가드/필터 ⑤ 스케줄러 ⑥ 캐시 계층.
**블로그 소재(각 1편):** 초과판매 재현기 / 락 4종 벤치마크 / NestJS→Spring 포팅에서 배운 것 / Redis 없이도 죽지 않는 캐시 설계.

## 15. 이 프로젝트로 증명할 수 있는 역량

- 동시성 제어를 **재현→해결→수치 검증**까지 완주 (신입 포트폴리오에서 가장 희소한 증거)
- 트랜잭션·인덱스·유니크 제약 등 **DB를 정합성 도구로 쓰는 능력**
- JWT Rotation·IDOR 방지·rate limit 등 실전 보안 감각
- 캐시 정합성에 대한 도메인 기준의 판단
- NestJS와 Spring **양쪽 생태계 이해** (스타트업+대기업 풀 동시 커버 — 내 스택 전략의 물리적 증거)
- k6·Grafana 기반 운영 관점 (인프라 지향 어필)

## 16. 면접 예상 질문 (12)

1. 초과판매를 막는 방법 4가지를 비교하고, 왜 조건부 UPDATE를 기본으로 선택했나?
2. `SELECT FOR UPDATE`로 여러 좌석을 잡을 때 데드락이 어떻게 발생하고 어떻게 예방했나? (좌석 ID 정렬)
3. 낙관적 락은 왜 이 도메인에 부적합한가? 적합한 도메인은 어디인가?
4. 서버가 2대가 되면 지금 설계에서 깨지는 부분은 어디인가? (로컬 캐시·스케줄러·rate limit)
5. Redis가 완전히 죽으면 어떤 기능이 어떻게 저하되나? 정합성은 왜 안 깨지나?
6. 선점 만료를 Redis TTL 하나로만 처리하면 안 되는 이유는?
7. Idempotency-Key를 Redis가 아니라 DB 유니크 제약으로 구현한 이유는?
8. Refresh Token 재사용이 감지됐을 때 정확히 무엇을 폐기하고, 왜 family 단위인가?
9. 좌석맵 캐시를 삭제 방식으로 무효화할 때 stampede는 어떻게 막나?
10. 부분 유니크 인덱스(`WHERE canceled=false`)를 쓴 이유는? 일반 유니크와 뭐가 다른가?
11. k6 결과에서 p95가 급증한 구간의 원인을 어떻게 추적했나? (커넥션 풀 고갈 사례로)
