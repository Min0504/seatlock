# 락 전략 벤치마크 — 좌석 선점 동시성 제어 4종 비교

같은 좌석에 동시에 몰리는 선점 요청을 직렬화하는 4가지 방법을 **전부 구현하고, 같은 부하로 측정**했다.
본선(main)은 조건부 UPDATE를 유지한다. 이 문서는 그 판단의 근거다.

## TL;DR

| | 결론 |
|---|---|
| 채택 | **조건부 UPDATE** — 대기 없음, 코드·인프라 최소, 초과판매 0을 DB 원자성 하나로 보장 |
| 명확한 열세 | **비관적 락** — 잠금 보유 구간이 가장 길어 모든 지표에서 뒤처지고, 부하가 오르면 락 컨보이(꼬리 지연 929ms)가 나타난다 |
| 조건부 우세 | **Redis 분산락** — 패자를 DB 앞에서 차단해 극단 경합에서 가장 빠르다. 대가는 승자 경로의 Redis 왕복(+8ms)과 장애 지점 추가 |
| 도메인 불일치 | **낙관적 락** — 이 벤치마크(재시도 없음)에선 준수하지만, 충돌이 기본값인 티케팅에선 "실패 후 재시도" 비용이 구조적으로 커진다 |

모든 전략에서 `hold_error = 0` — 어떤 전략도 초과판매나 5xx를 내지 않았다. 차이는 정합성이 아니라 **비용의 위치**다.

## 비교 대상

| 전략 | 원리 | 패자가 지불하는 비용 | 구현 |
|------|------|---------------------|------|
| 조건부 UPDATE (본선) | `UPDATE ... WHERE status='AVAILABLE'` 한 문장으로 검사+변경 원자화 | 행 락 대기열에서 승자 커밋을 기다린 뒤 "0건 갱신" 확인 | `main` — `SeatStateRepository.acquire` |
| 비관적 락 | `SELECT ... FOR UPDATE`로 행을 잠근 뒤 검사·변경 | SELECT 시점부터 줄을 선다 — 잠금 보유 구간이 select→commit 전체 | [`experiment/pessimistic-lock`](../../tree/experiment/pessimistic-lock) |
| 낙관적 락 | JPA `@Version` — 커밋(flush) 시 버전 비교로 충돌 감지 | 트랜잭션 전체를 실행한 뒤에야 실패를 안다(헛수고) + 재시도 | [`experiment/optimistic-lock`](../../tree/experiment/optimistic-lock) |
| Redis 분산락 | 좌석별 Redisson RLock을 MultiLock으로 묶어 `tryLock(대기 0)` — 실패자는 DB 진입 전 차단 | Redis 왕복 1회 (DB 커넥션 소비 없음) | [`experiment/redis-lock`](../../tree/experiment/redis-lock) |

실험 브랜치는 **머지하지 않고 보존**한다. 각 브랜치는 `HoldService.hold`만 교체하며 API 계약·통합 테스트는 동일하게 통과한다
(동시 100명 → 성공 정확히 1, 부분 선점 금지, 만료 선점 인수).

Redis 분산락 브랜치의 설계 원칙 하나는 강조할 가치가 있다: **락은 성능 계층이고, 정합성의 최종 권위는 여전히 조건부 UPDATE다.**
lease 만료·Redis 장애·락을 지나지 않는 쓰기 경로(만료 회수 스위퍼)가 있어도 초과판매는 DB가 막는다.
"분산락만 믿는" 설계는 락 소실 시나리오에서 무너진다.

## 측정 방법

- **환경**: 로컬(Apple Silicon), Docker PostgreSQL 16 + Redis 7, 앱 단일 인스턴스(HikariCP 기본 10), k6
- **데이터**: 회차 1개, 좌석 500, 사용자 100 (매 실행마다 DB 재생성 — `bench/run.sh`)
- **시나리오** (`bench/hold-contention.js`):
  - `single_seat` — 100 VU가 **같은 좌석 1개**에 1회씩 동시 돌진. 티케팅 오픈 순간의 최악 경합. 관심사는 "패자 99명이 얼마나 빨리, 어떤 비용으로 실패하는가"
  - `spread` — 50 VU가 40석 풀에서 무작위 좌석을 잡고 즉시 놓기를 20초 반복. 오픈 직후의 지속 경합. 관심사는 정상상태 p95와 처리량

**방법론상 한계** (숫자를 읽기 전에):

1. `single_seat`는 앱 기동 직후(JIT 워밍업 전)에 실행된다. 모든 전략이 같은 조건이므로 상대 비교는 유효하지만 절대값은 부풀려져 있다.
2. 실행 간 변동을 확인하기 위해 본선을 2회 측정했다 — `single_seat` p95는 149ms→116ms로 **±30ms 흔들리고**, `spread` p95는 34.2ms→34.7ms로 **1ms 안에서 재현**됐다.
   따라서 **`spread`(정상상태)가 1차 근거**이고, `single_seat`는 변동폭(±30ms)을 넘는 차이만 유의미하게 읽는다.
3. 단일 인스턴스 측정이다. 분산락의 본래 무대(다중 인스턴스)는 다루지 않는다 — 단일 DB의 행 락은 이미 인스턴스 수와 무관하게 안전하므로, 이 프로젝트에서 분산락의 가치는 "다중 인스턴스 대응"이 아니라 "DB 앞 차단"이다.

## 전략별 분석 — 숫자가 말하는 것

### 조건부 UPDATE (본선): 패자는 줄을 서지만, 그 줄이 가장 짧다

검사와 변경이 UPDATE 한 문장이므로 행 잠금은 **UPDATE 실행부터 커밋까지**만 유지된다.
패자는 승자의 잔여 트랜잭션만큼 대기한 뒤 0건 갱신을 확인하고 즉시 409로 빠진다.
`single_seat` avg 105ms가 그 대기 비용이고, `spread`에선 잠금 구간이 짧아 p95 34ms로 4종 중 최상위권을 유지한다.
**추가 인프라도, ORM 의존도, 예외 번역도 없다** — SQL을 실행할 수 있는 모든 경로(스위퍼, 수동 운영 쿼리)에서 같은 보장이 성립한다는 점이 운영에서 가장 큰 자산이다.

### 비관적 락: 잠금 보유 구간이 길다 = 모든 문제의 근원

`SELECT ... FOR UPDATE`가 잠금을 거는 순간부터 커밋까지 — 검증 로직, 보유 상한 계산, INSERT 준비가 전부 잠금 아래에서 실행된다.
같은 좌석의 경쟁자들은 그 전체 구간을 기다리므로 대기열이 가장 깊다(`single_seat` p95 218ms, 유일하게 변동폭 밖).
`spread`의 max 929ms는 **락 컨보이**다: 잠금 대기가 커넥션을 점유한 채 이어지면 풀(10개)이 마르고, 무관한 요청까지 커넥션 대기로 밀린다.
처리량도 23% 낮다(1,267 vs 1,650 req/s). 이 전략이 정당화되는 경우는 "잠근 상태에서 여러 번 읽고 검증해야 하는 다단계 로직"인데, 좌석 선점은 상태 전이 한 번이라 해당하지 않는다.

### 낙관적 락: 이 벤치마크가 오히려 유리하게 설계된 전략

읽기에 잠금이 없으니 정상상태 수치는 조건부 UPDATE와 사실상 동일하다(p95 34ms). 그런데 두 가지가 숨어 있다:

1. **헛수고 비용** — 패자는 조회·검증·flush까지 트랜잭션 전체를 실행한 뒤에야 실패를 안다. 시도의 절반 가까이(18,541/38,821)가 끝까지 실행하고 버려지는 작업이었다.
2. **재시도 증폭** — 이 벤치마크의 클라이언트(k6)는 409를 받으면 그냥 물러난다. 실사용에선 클라이언트든 서버든 재시도를 붙이는데, 충돌이 기본값인 티케팅에서 재시도는 부하를 배수로 키운다. "충돌은 드물다"는 낙관적 락의 전제가 이 도메인에선 성립하지 않는다.

구현 관점의 함정 하나: JPA의 버전 검사는 **flush 시점**에 일어나므로, 기본 flush(커밋 시)에 맡기면 예외가 트랜잭션 프록시 밖에서 터져 500이 된다.
서비스 안에서 명시적으로 flush해야 409로 번역할 수 있다 — 실패 지점이 ORM 내부에 숨는 것 자체가 이 전략의 유지보수 비용이다.

### Redis 분산락: 패자 비용의 위치를 바꾼다 — 그리고 그 대가

수치가 가장 극적이다. `single_seat` p95 62ms(패자 99명이 행 락 대기열 대신 Redis 왕복 1회로 탈락),
`spread` med 2.0ms(충돌 응답이 DB에 닿지도 않는다), 총 처리량 2,157 req/s(순간 탈락 → 다음 시도가 빨라져 시도 자체가 55% 증가).
**DB 커넥션을 패자가 소비하지 않는다**는 것이 본질이고, 이것이 "오픈 순간 커넥션 고갈"에 대한 구조적 해법이다.

대가는 세 가지다:

1. **승자가 느려진다** — 성공 요청 avg 25.1ms vs 본선 17.3ms. 모든 성공 경로에 락 획득/해제 왕복이 붙는다.
2. **충돌 판정이 거칠어진다** — 락은 "누가 이 좌석을 처리 중"만 알지 "좌석이 팔렸는지"는 모른다. 충돌 응답에 실패 좌석 정보(details)를 담을 수 없고, 처리 중인 요청과 겹치기만 해도 409가 난다(충돌 수 40,296 — 본선의 2.4배).
3. **장애 지점과 운영 복잡도** — Redis가 죽으면 선점 API 전체가 흔들린다. lease/대기시간 튜닝, 락 유실 시나리오 문서화가 따라온다.

단일 인스턴스 + DB 원자성으로 충분한 현재 규모에서 이 복잡도는 과잉이다. 다만 **경합이 커넥션 풀을 위협하는 규모**가 되면 첫 번째로 꺼낼 카드이고, 그 구현 원형을 이 브랜치가 보존한다.

## 왜 본선은 여전히 조건부 UPDATE인가

1. **정합성 보장에 조건이 없다.** 락 획득 성공 여부, ORM flush 시점, Redis 가용성 — 아무것도 전제하지 않는다. `WHERE status='AVAILABLE'`을 통과한 UPDATE만 상태를 바꾼다.
2. **성능이 목적에 부합한다.** 정상상태 p95 34ms, 처리량 1,650 req/s — 비관적 락을 명확히 앞서고 낙관적 락과 대등하며, Redis 분산락과의 차이는 "승자 +8ms vs 패자 -13ms"의 트레이드오프다. 티케팅에서 돈을 내는 쪽은 승자다.
3. **코드가 가장 단순하다.** 실험 브랜치들의 diff가 증거다 — 낙관적 락은 flush 시점 제어와 예외 번역을, 분산락은 락 생명주기와 트랜잭션 경계 분리를 추가로 요구했다.
4. **다음 병목의 해법은 락 튜닝이 아니다.** 경합이 지금보다 극단적으로 커지면(수만 동시 접속) 어떤 락을 골라도 DB 앞에서 무너진다. 그 시점의 정답은 대기열로 유입 자체를 제어하는 것(v4 계획)이고, 락 전략 교체는 그 전 단계의 미세 조정일 뿐이다.
